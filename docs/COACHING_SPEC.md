# RACR — Coaching Specification

**Version:** 1.0 (2026-07-29) · **Status:** Internally documented, describing behavior already implemented in code. Not yet reviewed by a qualified running coach or sports-science professional — nothing in this document is "coach-approved," and it must not be treated as production-approved coaching truth until that review happens.

This document is the coaching-rules half of the lightweight governance structure adopted from the Zaera Labs Running master prompt (see `docs/RACR_Master_Prompt.md` for the underlying product/behavioral-design spec, and `docs/SAFETY_POLICY.md` for the safety/escalation half). Its job is narrow: make the rules that already govern plan generation and adaptation *inspectable and versioned*, and honestly flag where they fall short of the fuller philosophy, rather than leaving that logic implicit and undocumented inside `app.js`.

Each section below cites the real function and location that implements it today, and carries its own status — **documented** (accurately describes shipped behavior) or **provisional** (a known, named gap against the target philosophy, not yet built). Runner classification, goal feasibility, and the two adaptation functions now live in `coaching-rules.js` (extracted 2026-07-29 from `app.js` for real automated test coverage — see `tests/coaching-rules.test.js` for extraction-fidelity checks and `tests/decision-scenarios.test.js` for the actual approved/forbidden-outcome decision library referenced throughout this document).

## Runner classification — documented

`classifyUser(profile)` (`coaching-rules.js`). Computes a level from recent behavior (`runDaysPerWeek`, `weeklyMileage`) via fixed thresholds (beginner ≤2 days or <8mi/wk; novice 3 days and <20mi/wk; intermediate ≤5 days and <40mi/wk; advanced otherwise), then takes the **more conservative** of that computed level and the runner's self-reported experience level. This already matches the master prompt's "primarily recent behavior, not a self-selected label" principle — self-report can only pull the classification down, never up.

**Injury/return-to-running status (fixed 2026-07-29):** a running-coach review flagged the previous binary "recent injury? yes/no" checkbox as too simplistic — it only ever capped classification at `novice`, with no distinction between a resolved injury and someone currently unable to run normally. Replaced with a 4-option onboarding enum, `profile.injuryStatus`, feeding `coaching-rules.js`'s `INJURY_CAP` lookup: `resolved` (no cap), `mild_discomfort` (caps at `novice` — the old binary "yes" behavior, unchanged for this case), `unable_to_run` (caps at `beginner`), `medically_restricted` (caps at `beginner`, plus an extra warning pushed onto the plan's warnings recommending professional clearance before starting — added in `finishWizard`, app.js, since `evaluateSafety`/`EVENT_TABLE` have no injury-aware lever of their own beyond the level cap). Existing plans created before this enum existed still work via a legacy-boolean fallback (`recentInjury: true` maps to the same cap as `mild_discomfort`). This onboarding-level status is a standing intake attribute, distinct from the separate per-workout `painGuidance()` triage — see `docs/SAFETY_POLICY.md`. `profile.injuryStatus` is also now passed to the AI coach's context (`coach.js`), which previously had zero injury signal beyond whatever the runner typed into a live chat message.

## Goal feasibility & plan length — documented, with a provisional gap

`evaluateSafety(event, weeksAvailable, level)` and `choosePlanLength(weeksAvailable, event, level)` (both `coaching-rules.js`). A per-event/per-level table (`EVENT_TABLE`) defines `minWeeks`/`idealWeeks`/`longRunPeak`/`peakVolume`/`taperWeeks`. If the runner's actual weeks-until-race is below `minWeeks` for their level, the plan is marked `unsafe` and a warning is surfaced recommending a later race date or shorter distance — the plan itself is never silently padded to look safer than it is.

**Provisional gap:** this is a binary outcome (unsafe warning, or not) rather than the master prompt's fuller feasibility taxonomy — there is no distinct "supported goal / unsupported goal / insufficient evidence / later-race recommended" output, and no separation between *completion* feasibility and *target-time* feasibility. Today a runner can get a plan generated even when only completion (not their stated goal time) is realistically supported, with no explicit call-out of that distinction. Not fixed in this pass — logged as the clearest next step for this section.

## Weekly structure — documented

`assignWeekTemplate(runDays, wantCross)` (`app.js`) assigns long/quality/easy/cross/rest to the week's 7 slots, always leaving at least one structural rest day. Phase progression (base → build → peak → taper → race) and numeric weekly-volume progression are computed in `buildStructuredWeeks()` before being formatted into label strings, specifically so the adaptive layer below can scale real numbers rather than re-parsing text.

**Frequency-aware opening schedule (fixed 2026-07-29):** the same coach review confirmed an exact bug — every new plan used to floor at a hardcoded 3 running days/week regardless of the runner's actual current frequency (`Math.max(3, ...)`), so someone currently running zero days could be handed 3 running days immediately. `coaching-rules.js`'s `startRunDaysFor`/`runDaysForWeek` fix this: the opening week starts at the runner's real current frequency **plus one** (never below 2), then ramps by exactly one running day every 2 weeks until reaching the plan's eventual target day count — the same "no more than one additional day at a time" principle applied to the whole ramp, not just week one. Applies uniformly regardless of run-walk mode (an orthogonal axis — day *count* vs. session *content*), so a true beginner gets both a gentler day-count ramp and the run-walk intensity progression together.

**Quality-day volume math (fixed 2026-07-29):** quality-day sessions ("6 x 400m @ 5K pace") used to always show `miles: 0` in the generated plan, even though `buildStructuredWeeks` already computes a real `qualityMiles` session-distance budget internally to correctly size down that week's easy runs — it just never attached that number to the quality day itself, so weekly planned-distance totals silently excluded it. `day.miles` is now set to that budget whenever it's nonzero, and the label gets an honest suffix (`"...(~3 mi total, incl. warm-up/cool-down)"`) framing it as a holistic session estimate — **deliberately not** a precise parse of the label's interval structure (many `QUALITY_POOL` entries, e.g. `"Fartlek: 8 x 1 min hard / 1 min easy"` or `"Medium-long run"`, have no clean numeric structure to parse in the first place). Companion fix: `interpretRunResult`'s "you came up short of the planned distance" message is now excluded for quality days (matching how the "ran notably farther" message already was) — otherwise a runner logging only their hard-interval distance, a plausible habit for "6 x 400m," would get an inappropriate short-fall message for a workout completed exactly as prescribed.

## Recurring workouts / existing commitments — documented, provisional classification (new 2026-07-31)

A "World-Class App Developer" master prompt (applying its own real-world-commitments framework to this app specifically) asked for the app to account for workouts the runner already does outside the plan — a spin class, yoga, strength training — rather than treating the runner as if the running plan were their only commitment.

**Data model**: `state.recurringWorkouts`, an array of `{id, activityType, customName, day (0-6 or null), durationMinutes, intensity, fixed}` records — Settings-editable any time (mirrors `state.unavailable`'s list/add/remove UI), optionally seeded during a new-plan onboarding step. `day` is `null` for movable workouts. Editing an existing plan through the wizard never touches this list — Settings is the sole editor once a plan exists, so re-running the wizard can't silently discard workouts added later.

**Classification** (`coaching-rules.js`'s `RECURRING_ACTIVITY_PROFILE`/`classifyRecurringWorkout`) uses two deliberately independent axes per activity type, since conflating them breaks real cases: `contribution` (aerobic/strength/mobility — inherent to the activity, used only to avoid double-crediting work the runner already gets elsewhere) and `maxHardness` (the ceiling of how hard the activity type can realistically get). Combined with the runner's own reported `intensity`, `maxHardness` — not `contribution` — decides `isHardDay`: an easy spin is aerobic-contributing but never a hard day; hot/power yoga (reported `intensity:'high'`) becomes a hard day despite yoga's normally-gentle nature; walking never becomes a hard day regardless of reported intensity, a deliberate conservative cap. **This is a coaching judgment call, not clinically or coach-reviewed** — same provisional status as every other rule in this document.

**Scheduling integration** (`buildStructuredWeeks`): fixed workouts override their exact designated weekday's slot — **except the long-run slot, which is never overridden** (a fixed workout landing there is a real conflict, surfaced as a warning, never silently resolved, matching the master prompt's rule that cross-training must never replace running-specific impact/tissue adaptation). Movable workouts consume the plan's own auto-generated cross-training slots instead of occupying a dedicated one. A fixed hard workout demotes that week's quality/interval session to easy (same-day-and-week stacking avoidance only — not a full multi-day adjacency model). A recurring workout with real strength contribution reduces that week's auto `"+ Strength"` budget so the total never exceeds `STRENGTH_SESSIONS[phase]`'s intended weekly count. `evaluateRecurringWorkoutSchedule` warns (via the same `planMeta.warnings` mechanism `evaluateSafety` already uses) when fixed commitments plus required running days would leave no room for a rest day, or when a fixed workout targets the long-run day.

**Weekday-to-slot mapping (fixed 2026-07-31, caught by live onboarding verification before push):** a recurring workout's `day` is a real calendar weekday (Mon=0...Sun=6), but `dateForSlot` anchors slot 6 to whatever weekday the race itself falls on — not always Sunday. The initial implementation assumed slot 0 was always Monday, which only holds when the race happens to land on a Sunday; for any other race weekday, a runner who picked "Tuesday" as their fixed day would see their session placed on the wrong day entirely (confirmed live: a Saturday race put a "Tuesday" spin class on Monday instead, leaving the auto-generated cross-train pick sitting on the real Tuesday). `slotForFixedDay(raceDate, day)` now inverts `dateForSlot`'s math to find the correct slot for any race weekday, used everywhere a fixed workout's slot is needed (`buildStructuredWeeks`'s placement/exclusion logic and `evaluateRecurringWorkoutSchedule`'s long-run-day conflict check, which now takes the race date as a third argument). Covered by `tests/recurring-workouts.test.js`'s "the same weekday chip maps to a different slot depending on what weekday the race itself falls on" test, comparing a Sunday-race and Saturday-race plan side by side.

**Explicitly not built, per the master prompt's own scoping**: one-time exceptions/cancellations, calendar-time-of-day management, a full workload-scoring/optimization engine, multi-day adjacency-graph analysis beyond same-week stacking. `applyMissedAdjustment`/`applyDifficultyAdjustment` don't yet know about recurring-workout days specifically (they key off `day.miles`, which recurring-workout cross days don't set) — a real follow-up, not attempted here.

**Quality-slot conflict "smart" handling (new 2026-07-31, per an explicit product decision)**: the quality/speed-work slot is structurally always slot 1 whenever a week has ≥2 running days (`RUN_SLOT_PRIORITY`'s first entry), so a fixed workout landing there recurs identically every such week for the whole plan, not as a one-off. A **hard** fixed workout there (e.g. a Tuesday HIIT class) is treated as a fine substitution for that week's hard-day role — no schedule change, just an explanation (see below), since the existing hard-day-demotion guard already prevents doubling up. A **non-hard** fixed workout there (an easy spin, gentle yoga) would otherwise silently and permanently erase structured speed work for the entire plan, so `buildStructuredWeeks` now performs one deterministic swap: if that week's template has a spare `'easy'` slot, quality relocates there instead of disappearing. This is a single bounded swap, not a general optimizer, and it only ever considers the ORIGINAL template's easy slots (no cascading re-solves). When a week has no spare easy slot to relocate to (only possible at very low run-day counts, e.g. `targetRunDays<=2`), there's nothing to move it to — `evaluateRecurringWorkoutSchedule` surfaces that as an explicit warning instead of solving it.

**Plan explanations (new 2026-07-31)**: `generateRecurringWorkoutNotes(recurringWorkouts, raceDateIso)` produces short, positive, plain-language sentences describing how each recurring workout affects the plan (a movable workout "counts as this week's cross-training," a fixed strength session "fulfills this week's main strength session," a fixed hard workout on the quality slot "covers this week's hard session," a fixed easy workout there triggers the relocation note above) — shown in Settings next to the recurring-workout list, not buried in the calendar. Deliberately static (computed once per workout, not simulated week-by-week) since every effect described recurs identically for the whole plan, given the race date never changes mid-plan.

## Adaptation rules — documented, one gap fixed, several actions still unbuilt

`applyMissedAdjustment(weeks, raceGoal, planMeta, logs, today, terrainNote, units)` and `applyDifficultyAdjustment(...)` (both `coaching-rules.js`). Today's adaptation logic works at a **whole-week aggregate level over core running sessions**: if more than 60% of last week's easy/quality/long sessions went unlogged, all future non-race weeks are dampened ~15%; if specifically the long run was missed, only the next long run is shortened ~20%. Neither ever adds make-up mileage or doubles a future session to compensate for a miss — that non-negotiable already holds.

**Fixed (2026-07-29):** the ratio used to count cross-training days as equally diagnostic as real running work, so several unlogged cross-training sessions alone could trip the same 60% threshold as actually missed running — incorrectly dampening the quality session and long run over what was really just skipped optional supportive work. Cross-training is now excluded from the missed-ratio entirely, the same treatment `rest`/`race` days already got — matching the master prompt's own worked example (miss Tuesday's easy run, plus some optional cross-training; Thursday's quality and Saturday's long run stay untouched) exactly. `tests/decision-scenarios.test.js` covers this directly: an isolated cross-training-only miss never triggers anything, while a genuine core-running disruption (several easy/quality/long sessions actually missed) still correctly triggers the dampen — confirming the fix removed false positives without making the engine too lenient.

**Still not built, honestly:** this remains a *corrected ratio*, not the master prompt's full per-session action model. The engine only ever does three things — `preserve` (no-op), `shorten` (next long run, on an isolated long-run miss), or `reduce` (future volume dampening, on real core-running disruption). The other six named actions (`move` / `substitute` / `remove` / `rebuild` / `pause` / `escalate`) don't exist here: there's no rescheduling, no side-quest substitution offered automatically, no distinct "extended interruption" rebuild mode, and `pause`/`escalate` are deliberately left to the separate pain-triage/illness system (`docs/SAFETY_POLICY.md`) rather than duplicated in this engine. Building those remains a real, larger future option, not attempted in this pass.

**Partial-session credit (fixed 2026-08-02):** the missed-ratio loop used to do a bare truthiness check on the log entry (`if (logs[key])`) — a `completionType: 'stopped_early'` or `'partial'` session counted identically to a fully completed one. Now gives half credit for those two completion types specifically, so a week of several half-finished sessions no longer silently passes the 60% missed-ratio threshold the way a week of fully-completed ones would. A stopped-early/partial **long run** specifically also now triggers the same next-week shortening treatment a fully-missed long run gets, rather than being silently treated as a full completion just because something was logged.

**Adjustment re-capping (fixed 2026-08-02):** neither `applyMissedAdjustment`'s dampening nor `applyDifficultyAdjustment`'s RPE-driven nudge previously re-checked their result against any safety ceiling — a run of several low-RPE weeks could in principle nudge volume up indefinitely with nothing to stop it. Both now re-derive the same event-level `longRunPeak`/`safetyScale` `buildStructuredWeeks` itself uses and clamp the result against it (`adjustmentCaps`/`clampAdjustedMiles`). **Known, disclosed simplification:** this re-derivation doesn't replicate the tighter base-phase `longRunSafetyCap` (`profile.longestRun * 1.15`), since these adjustment functions don't receive `profile` — the event-level peak is still a real, meaningful ceiling, just not the tightest one theoretically possible.

**Illness/vacation return-to-training ramp-back (fixed 2026-08-02):** `applyUnavailableRanges` used to convert affected days to rest and stop there — the very next scheduled day after even a multi-week break returned straight to full target volume, with no ramp-back. Breaks of 7+ days now get a bounded, proportional easing-back period on easy/long days for the 7 days immediately following the break (`rampFactor = max(0.6, 1 - breakDays/60)`, floored so even a very long break never drops below 60% of planned volume for that window). Breaks under a week are left alone — the existing missed-workout/RPE adjustments already cover ordinary short disruption, and not every missed day needs a dedicated ramp.

**Hard-day spacing (fixed 2026-08-02):** the existing hard-day-stacking guard for recurring workouts only ever checked same-slot conflicts against the quality session, never adjacency (the day immediately before/after the long run or quality slot) and never a runner's *cumulative* weekly hard-day count. `evaluateRecurringWorkoutSchedule` now also warns when a fixed hard workout lands the day before/after the long run or quality slot, and when total hard days (recurring hard workouts + the plan's own quality session) would exceed 2 in a week. Detected and warned, not rescheduled — a fixed workout's day can't be moved by this app (it's fixed by definition), the same reasoning the existing long-run-day-conflict warning already uses.

**Race-week shakeout (fixed 2026-08-02):** every non-race day in race week used to become unconditional rest. Novice+ levels (not true beginners, matching this project's existing conservative bias for that level) now get one short (≤2 mi) easy shakeout run 2 days before race day instead — standard practice for most runners, not required, clearly labeled "(shakeout)" in the day's own text.

**PR/aggressive-goal evidence (fixed 2026-08-02):** selecting a `pr` or `aggressive` goal used to apply its full volume multiplier (1.05x/1.12x) regardless of whether the runner had any recent race result to calibrate against. `effectiveGoalFactor`/`hasRecentRaceEvidence` now cap the factor at the `improve` level (1.0x) when no real evidence exists, with an explanatory warning (not a block — the goal choice itself is never refused) — a PR goal with zero supporting evidence is really just an ambitious "finish" goal wearing a bigger multiplier.

**Run/walk persistent opt-out (fixed 2026-08-02):** the run/walk progression window used to always span roughly the first 60% of the plan, transitioning every runner to continuous mileage by the end regardless of preference — continuous running was implicitly required for a "complete" plan. `profile.preferRunWalkThroughRace` (surfaced as a wizard question, shown only when the runner has already said they can't run continuously) now spans the run/walk window across the *entire* plan when set, so run/walk intervals can persist all the way to race day for runners who prefer them.

**Long-run share cap (fixed 2026-08-02):** `longShare` (the fraction of weekly volume the long run consumes) was uncapped — reaching 45% for a 3-day/week 10K runner, and higher still for ultra events whose own baseline share is already elevated (e.g. 100mi's 0.40 base + a 0.15 low-frequency bump = 0.55). Now capped at 50% regardless of event/frequency — high, but a real ceiling, and ultra events legitimately run a higher baseline share than road races.

**Quality workout consistency (fixed 2026-08-02):** `QUALITY_POOL` entries were bare label strings; the displayed distance (`qualityMiles`) was computed completely independently of what the label actually described (`targetVolume * 0.18`, capped at 8mi) — a 20-minute tempo and a 5x1000m interval session could show the same distance purely by coincidence of the week's overall volume, with zero connection to the entry's own structure. Entries are now `{ label, estimatedMinutes }` objects, with `estimatedMinutes` mechanically built from each entry's own stated structure (10 min warmup + reps × (work + jog recovery) + 10 min cooldown for interval/tempo sessions; a flat representative time for the ultra events' continuous-effort/rehearsal entries, which aren't real interval sessions). Distance is now derived FROM that same number via a documented, deliberately generic pace assumption (`QUALITY_DEFAULT_PACE_MIN_PER_MI = 10` — not the runner's own actual pace, which isn't reliably known without a recent race result), then still capped against the week's own volume budget exactly as before, so a long structured session never exceeds what the week can safely hold. Own synthesis (same standing as `RUN_WALK_STAGES` elsewhere in this document), not a lab-measured figure.

## Race readiness — documented (new 2026-08-02)

**Genuine minimum-readiness check, not just calendar length:** `evaluateSafety`'s `weeksAvailable < cfg.minWeeks` check never read the runner's own current fitness at all — a true beginner starting from a 1-mile longest run and a runner already at 8 miles passed the identical check for the same event/level. `evaluateReadiness(profile, raceGoal, level, weeksAvailable)` (`coaching-rules.js`) adds a real check: how many weeks it would take to safely grow the runner's *own current longest run* to the event's expected long-run peak, using the standard, widely-used "10% rule" progression rate (`weeksToGrowDistance`) — not `computeWeeklyVolumes`'s own weekly-volume ramp, which (caught while building this) essentially never reaches `EVENT_TABLE`'s nominal `peakVolume` even across a full `idealWeeks`-length plan for a realistic starting profile; a separate, deeper finding about that ramp formula's calibration, disclosed here rather than silently patched as part of this fix.

When infeasible, `formatReadinessWarning` computes **concrete alternatives** instead of a vague "consider a later date or shorter distance": how many additional weeks would make the current distance feasible, and the largest shorter event (walking `5k → 10k → half → marathon → ...` downward) that already fits the runner's current timeline. `planMeta.unsafe` now folds both checks together (`safety.unsafe || !readiness.ready`) so a readiness-only failure still triggers the plan's existing volume-scaling mechanism (`safetyScale`) — this required fixing `safetyScale`'s own denominator too (`effectiveMinWeeks = max(cfg.minWeeks, planMeta.neededWeeks || 0)`), since the original formula assumed `unsafe` only ever meant "not enough calendar weeks" and would have silently applied zero scaling for a readiness-only failure where the calendar happened to look adequate.

Deliberately advisory only, never a block — matching the explicit product decision that runners know their own situation better than this app does, and that gating erodes trust rather than building it (see also the injury-status warnings in `docs/SAFETY_POLICY.md`).

**Post-generation adequacy check, closing the previously-disclosed gap (new 2026-08-02):** the paragraph above disclosed that `computeWeeklyVolumes`'s real ramp grows slower than the 10%-rule estimate `evaluateReadiness` uses — meaning a runner could be told `ready: true` and still receive a plan whose actual peak volume and long run fall well short of `EVENT_TABLE`'s targets, silently, with no warning. A review of this feature flagged that gap as the central unresolved release blocker: `evaluateReadiness` certifies a *hypothetical* plan, not the one the runner actually gets.

`evaluatePlanAdequacy(weeks, raceGoal, planMeta, profile)` (`coaching-rules.js`) closes it by inspecting the ACTUAL generated `weeks` after `buildStructuredWeeks`/`generatePlan` runs — the real peak weekly volume and real peak long run the plan reaches (excluding the taper/race week, which is intentionally reduced) — and comparing both against `EVENT_TABLE`'s `peakVolume`/`longRunPeak` with an 85% tolerance. Falling short of either marks the plan `adequate: false`, and `finishWizard` (`app.js`) appends a second, concrete warning (`formatPlanAdequacyWarning`) citing the actual numbers reached versus the event's real targets — distinct from, and in addition to, `evaluateReadiness`'s pre-generation estimate, since a plan can pass the estimate and still fail this check (confirmed against the exact reported scenario: a beginner starting from a 2-mile longest run given 18 weeks to a half marathon shows `ready: true` but generates a plan peaking at ~8.5 mi/week and a 4-mile long run against the event's 22 mi/week / 9-mile targets — see `tests/plan-scenarios.test.js`).

The 85% tolerance is a coaching judgment call, not clinically reviewed — a plan landing close to but not exactly at its nominal peak (rounding, a taper phase, a plan ending slightly early) shouldn't itself be flagged, only a material shortfall should. Frequency (the actual peak running-day count reached vs. `targetRunDaysFor`) is computed and returned but deliberately **not** part of the adequate/inadequate verdict: a fixed recurring workout can legitimately occupy what would otherwise be a running slot (see "Recurring workouts" below), so a lower running-day count doesn't by itself signal an inadequate plan the way a volume/long-run shortfall does. A runner who opted into run/walk through race day (`profile.preferRunWalkThroughRace`) never has a continuous-mileage long run to measure at all — an intentional, separately-disclosed choice (see "Run-walk programming"), not a plan defect — so `longRunApplicable: false` skips that half of the check for them rather than always failing it; the volume check still applies.

**Explicit gap, not addressed by this pass:** this check still doesn't attempt to auto-suggest a shorter event or longer timeline the way `evaluateReadiness`'s pre-generation `alternatives` does — doing that correctly would mean actually re-running generation for each candidate event/timeline rather than reusing the (already-shown-to-be-optimistic) 10%-rule projection. `formatPlanAdequacyWarning`'s text suggests "more weeks or a shorter distance" in general terms without simulating which one would actually work.

Also fixed in this pass: `formatReadinessWarning`'s text previously said "Based on your current weekly mileage," which was never true — the underlying calculation (`weeksToGrowDistance`) has only ever used `profile.longestRun`. Now reads "Based on your current longest run."

## Launch scope — documented (updated 2026-08-02)

Public launch is scoped to **5K, 10K, and half marathon**. Marathon/50K/50-mile/100K/100-mile plan generation remains fully implemented and tested in the codebase (unchanged, not deleted) but is held behind the `state.flags.enableLongerDistances` feature flag (see the app's Settings → Beta features), hidden from the public onboarding wizard's event picker by default until each distance family has been separately reviewed. See `docs/SAFETY_POLICY.md` for the corresponding safety-review gate. The visibility rule itself is a pure, unit-tested function (`coaching-rules.js` `visibleEventsFor`, shared by app.js instead of duplicating the filter) — editing an existing longer-distance plan always keeps that plan's own event selectable regardless of the flag, so toggling the flag (or a fresh install that never enabled it) never strands an existing plan.

## Session-level architecture — documented (new 2026-08-02)

`day.sessions[]` (`coaching-rules.js` `buildStructuredWeeks`) gives every planned or recurring workout a structured object (id/role/activityType/purpose/structure/rpeRange/loadClass/status/explanation/label, etc.), regenerated fresh on every plan computation from a **deterministic id** (`sessionIdFor(weekNum, slot, role, suffix)`) that stays stable across regeneration as long as the underlying session keeps landing on the same week/slot/role.

The **primary** session on every day (the overwhelming majority of days) continues to use the existing date-keyed `state.logs`/`state.overrides`/`state.crossType` exactly as before — zero migration risk, zero behavior change. A **secondary** same-day session (e.g. an 11am spin class riding alongside a morning run, or a second fixed workout sharing a non-running day) has no day-key of its own to safely share, so it gets independent state keyed by its own stable session id: `state.sessionLogs`/`state.sessionOverrides`, with `getSessionLog`/`setSessionLog`/`getSessionOverride`/`setSessionOverride` (app.js) mirroring the existing `getLog`/`setLog` shape. Both new maps merge via the same `mergeMap` (`merge-state.js`) already used for `logs`/`overrides`/`crossType` — per-key newer-device-wins, so two sessions on one date can never overwrite each other during sync. Skipping/removing a session is modeled as **writing a tombstone override** (`{skipped:true}`), never deleting the key outright, so a sync merge can't silently resurrect a session the runner deliberately removed on another device.

The weekly calendar (`renderMain`) renders a genuinely separate, independently-clickable row for every secondary session (in addition to the primary row's existing label-suffix hint), opening `renderSessionDetail` — its own screen showing the session's real purpose/structure/RPE/duration (the same purposeful cross-training prescriptions `buildCrossTrainingPrescription`/`buildHikePrescription`/incline-walk builders already generate) with independent log/skip actions. Verified live in-browser against the benchmark customer: Monday's run and 11am spin, and Tuesday's Tabata + 12-3-30 (two fixed workouts sharing one non-running day), each render as separate rows, open independently, and log independently without affecting the other.

**Known, deliberate scope limit**: this pass builds independent *view/log/skip* for a secondary session, not full replace/move parity with the primary flow (no pace-zone analysis, no planned-vs-actual review, no XP integration) — a smaller, purpose-built screen rather than duplicating `renderWorkoutDetail`'s full depth for what's usually a fixed class with nothing to compare against a target pace. A full "Replace workout" action (with purpose-preservation classification, per the product spec) is not yet built for either primary or secondary sessions.

## Unplanned hard-workout adaptation — widened (updated 2026-08-02)

`applyEveningIntervalAdaptation` previously only ever inspected the single next calendar day. It now scans the full 48–72 hour window (the next 1–3 calendar days), stopping at the first genuinely conflicting hard day found: a quality run (downgraded to easy recovery pace, as before), a fixed hard recurring commitment such as a Tabata class (marked `reduced` in place — the same treatment already used for a long-run/fixed-workout conflict, see "Constraint-aware scheduling" below), or an easy day (lightened). The long run and race day are still never touched regardless of where they fall in the window, and a day already resting is left alone. Stops after the first adaptation rather than downgrading every day in the window, since one unplanned hard session doesn't warrant defanging the whole 72 hours.

## Today screen actions — documented (new 2026-08-03)

Four explicit, in-the-moment actions on `renderWorkoutDetail` (app.js): **Skip**, **Shorten**, **Postpone**, **Reschedule**. All four are the runner's own deliberate choice, never automatic, and none of them earn or lose XP as a form of judgment.

**Skip** — no new state or pipeline function. Writes `completionType: 'skipped'` onto the day's existing log entry (`app.js` `skipWorkout`, deliberately not `logAndCelebrate` — a skip must never trigger a celebratory toast or milestone check). `xp-system.js`'s `COMPLETION_MODIFIERS.skipped = 0` — neither rewarded nor punished, matching this project's standing anti-guilt rule. Rendered as a distinct calendar icon (`day-status--skipped`), separate from both "done" (a check) and "missed" (an unlogged gap nobody decided) — a skip is a tracked fact, not a silence.

**Shorten** and **Postpone/Reschedule** are real, deterministic pipeline functions in `coaching-rules.js`: `applyShortenAdjustment`/`applyMoveAdjustment`, driven by `applyDayAdjustments` — the final step of `generatePlan`'s pipeline (after every automatic adaptation), so the runner's own explicit choice is never silently re-adjusted by a rule. Keyed by day-key (`state.dayAdjustments`, same shape/merge semantics as `logs`/`overrides`).

- **Shorten**: reduces an easy/long day's miles by a factor (default 0.7, i.e. "about 30% less") and relabels it; a quality day keeps its structured prescription verbatim and appends a plain-language "cut the reps/intervals by about X%, same pace/effort" instruction instead of guessing new intervals; a cross/recurring-workout day reduces its stated duration. `day.sessions[]`'s primary entry is kept in sync (rebuilt via `buildRunSession` for running types; updated in place for cross types) — the same staleness class of bug already fixed once for travel overrides, caught again here during live verification and fixed the same way. Toggling the button again fully undoes the adjustment.
- **Move** (Postpone = one tap to tomorrow; Reschedule = a day-picker for the next 13 days) relocates a running day's (easy/quality/long only — see scope note below) content to another day. The **source day's own coexisting secondary session** (e.g. a same-day spin class) deliberately stays where it is — only the primary running content moves. The moved label is built from the **source's primary session's own clean label**, not `day.label` (which can carry a same-day secondary-session suffix like "+ 45 min Spinning / Cycling") — a real bug caught and fixed during live verification, where the destination day briefly claimed to include a class that never actually happens there. The picker shows, and the confirm dialog states, when a target day already holds a long run or quality session that would be replaced (`describeMoveConflict`) — informational only, per the product rule "warn, don't block."

**Scope, stated plainly**: Move only applies to real running days (easy/quality/long) this pass — a recurring-workout ('cross') day has its own separate recurrence rules and moving it is a materially harder problem, not built here. Race day can never be a source or a target for either action. The day-picker is bounded to the next 13 days, deliberately short of a full remaining-plan browse, so a reschedule can't silently land past a taper cutoff without the runner noticing how far they've pushed it.

## Error handling — two gaps fixed (new 2026-08-03)

Two concrete gaps from the V1 launch audit:

- **`saveState` had no error handling at all** — a `localStorage.setItem` failure (quota exceeded, private-browsing storage disabled, corrupted storage) threw uncaught, crashing whatever click handler triggered it, with no indication to the runner of what happened or whether their data was safe. Now wrapped in try/catch: the failure is reported via the existing `reportError`/telemetry path, and the runner gets a plain-language toast ("Couldn't save that — your browser storage may be full... this change will be lost on reload... try Export data, then free up space") that states what happened, that this specific change is at risk, and what to do about it — the in-memory `state` object itself is always still correct (`loadState()` runs exactly once at startup, so a failed write is never later overwritten by a stale re-read). Throttled to one notice per failure streak, not one per tap, since a full quota fails identically on almost every subsequent action until the runner frees up space; a later successful save resets the throttle so a fresh problem still gets a fresh notice.
- **A wholly past (or same-day) race date could slip through onboarding.** The wizard's own validation only checked "start date is before race date" and clamped a past *start* date up to today — neither catches a past *race* date, which after the clamp left `startDate` (today) sitting after `raceDate`, an inverted range that would send nonsensical values into `choosePlanLength`/the calendar's date math. Now rejected outright with a plain-language alert before the wizard advances past the race step.

Both live-verified (a monkeypatched `localStorage.setItem` throwing `QuotaExceededError`, and a `2020-01-01` race date typed into the wizard) rather than unit-tested — `app.js` isn't part of the automated test harness (browser-only IIFE, same as every other UI-only fix in this document).

## Accessibility — improved (new 2026-08-03)

An audit against the V1 launch spec found this area "genuinely weak" — the app's primary navigation (the five header icons present on nearly every screen) had no `aria-label`, no keyboard handling, and no semantic role: bare `<i>` tags with only a hover `title`. Fixed by converting every non-semantic clickable `<div>`/`<span>`/`<i>` in `app.js` to a real `<button>`, so Tab/Enter/Space, a native focus ring, and an accessible name all come for free instead of being hand-reimplemented:

- **Header nav** (`headerIconsHtml`) — 5 icons, now real buttons with `aria-label` (Progress/What this all means/Safety info/Install app/Edit plan/Settings); zero change to `wireHeaderIcons`'s click-wiring since a button's `id` works with `getElementById` exactly like the old `<i>` did.
- **Bottom tab bar** — already real buttons with visible text; added `aria-current="page"` on the active tab and `aria-hidden` on its decorative icon.
- **Calendar day-row** — the date button that opens a day's detail screen now has a real accessible name (the full date + what's planned, not just "MON 3"); the inline-editable workout label is a real button too; a secondary same-day session's whole card is a real button (no nested interactive children to conflict with).
- **`.ob-cancel`/`.pain-toggle`** (Back/Cancel/"Not feeling this run?"/"Report pain"/etc., 22 call sites across the app) — batch-converted from bare `<div>`/`<span>` click targets to real `<button>` elements; CSS resets keep every one visually identical to before (one exception, `.cross-segment-remove`, needed an explicit inline-width override since it sits in a flex row, not on its own line).
- **Chip selection state** (`chipsHtml`, RPE chips) — selection was signaled by color alone (border/text/background tint), which a screen reader can't see at all. Every chip now carries `aria-pressed`, set on initial render and kept in sync by the same `classList.toggle('selected', ...)` call sites that already existed (22 sites, all following one consistent pattern).
- **Global focus-visible fallback** — one rule covering every interactive element, so nothing relies on the browser's inconsistent default outline; the three places that had explicitly removed the outline (`.ob-input`, `.cross-select`, `.day-plan-edit`) got a supplementary `box-shadow` ring instead of losing focus visibility entirely.
- **Reduced motion** — checked, not just assumed: the entire stylesheet has exactly one `@keyframes` animation, and it was already correctly gated behind `prefers-reduced-motion: no-preference`. Nothing further needed here.

**Known, real, NOT fixed this pass**: ~70 form fields across the wizard/Settings/workout-detail screens have a visible `.ob-label` div next to their input with no programmatic association (`label[for]`/`aria-labelledby`) — a screen reader can't reliably announce what a given field is for. This wasn't safely batchable by regex (label and input live in separate string segments, sometimes with conditional rendering), so it's flagged as a scoped follow-up rather than rushed or silently skipped.

## Subscription / premium features — freemium model built, real purchase flow NOT yet possible (new 2026-08-03)

Runner is freemium. **Free for everyone, no matter what**: the training plan itself, all safety/pain guidance, logging, the calendar, recurring workouts, travel mode, weight tracking, and progress tracking. Only two features that cost real per-use backend/AI spend are gated (`subscription.js`'s `PREMIUM_FEATURES`): **AI coach chat** and **Google Health / Fitbit sync**. This split, and which two features are gated, was a product judgment call made without a further ask, on the reasoning that safety-critical and core-training features must never be paywalled (an explicit standing rule of this project) while the two gated features are genuinely optional conveniences with a real recurring cost to run.

`state.subscription = { tier: 'free'|'premium', productId, source: 'ios'|'android'|null, expiresAtIso, willRenew, lastVerifiedIso }`. `subscription.js` (`hasActiveEntitlement`, `isFeatureLocked`) is pure and unit-tested — a premium record with no `expiresAtIso` on file is treated as active rather than locking out someone who's already verified as paid. Cross-device merge (`merge-state.js`) deliberately does **not** follow the plain prefer-newer-`lastModified` pattern every other scalar field uses: since this field protects something the runner actually paid for, an active entitlement on either device always wins outright, falling back to newer-`lastVerifiedIso`-wins only when neither (or both) sides are currently active. Gated at the two entry points (`app.js` `openCoachChatOrUpgradePrompt`, the `ghConnectBtn` handler) rather than inside the features themselves, so a screen already open for an already-entitled runner is never interrupted mid-use if a subscription happens to lapse.

**What this pass explicitly did NOT build, stated plainly**: a real Apple/Google in-app purchase flow. StoreKit (iOS) and Google Play Billing (Android) are native-platform APIs — they do not exist inside a browser, and this project is a pure vanilla-JS PWA with **no native app shell at all** (confirmed: `package.json` has zero dependencies, no Capacitor/Cordova/React Native config anywhere in the repo). Real IAP requires, at minimum: wrapping this PWA in a native shell (Capacitor is the lowest-friction option that doesn't require rewriting the existing HTML/JS/CSS — consistent with this project's standing "extend the existing vanilla JS PWA, don't rewrite it" rule), a receipt-validation/entitlement layer (RevenueCat is the common off-the-shelf choice specifically because it unifies Apple+Google receipt validation instead of hand-rolling both), and real product listings created in App Store Connect / Google Play Console — none of which can be set up from inside a coding session (they need developer-account enrollment, Xcode/Android Studio, and real store submission, all outside this repo). Until that exists, `renderUpgradePrompt` shows an honest "subscriptions aren't open yet" screen with a disabled button rather than a fake working "Subscribe" flow — this project's standing honesty rule (never claim a feature is complete when it isn't) applies exactly as much to a paywall as to anything else.

## Achievements — XP and generic player levels removed (new 2026-08-03)

**Product decision**: XP, generic player levels, and rank titles (`xp-system.js`, `state.xp`/`xpEvents`/`xpProfile`) are removed from V1. They never influenced training, readiness, adaptation, or safety, so per the standing "no isolated points/badges/levels disconnected from meaningful training behavior" rule, they didn't belong in the shipped experience. `docs/RACR_Reward_System_Master_Prompt.md` and `docs/RACR_Leveling_System.md` (the two docs that specified the XP economy) are marked superseded, kept only for history.

**Replaced with real, verifiable running achievements** — two kinds:

- **One-time badges** (`state.badges`, awarded exactly once via the same `indexOf === -1` pattern already used for Side Mission/challenge/quest-track badges): First Run, First Mile/Kilometer (unit-aware label), First 5K, First 10K, Four Consistent Weeks, Training Plan Complete (fires when race day itself is logged — every plan in this app ends on race day, so finishing it IS finishing the plan; a separate "Race Day Complete" badge would describe the identical real-world event, so this app doesn't invent two badges for one moment).
- **Recurring personal-record celebrations** (no permanent badge — a new one happens again and again, so a badge would only ever fire once and then go stale): Longest Run Yet and fastest-pace-per-workout-type (pre-existing `checkForMilestone`, unchanged, just decoupled from XP) plus a new Highest Weekly Mileage Yet (`checkForWeeklyMileageMilestone`) using the same "needs a real prior best to beat" rule.

**Four Consistent Weeks** (`weekCompletionRatio`/`trailingConsistentWeeksCount` in `app.js`) reuses `coaching-rules.js`'s own missed-ratio exclusions (rest/race/cross days don't count, `stopped_early`/`partial` earn half credit) at an 80%-completion bar, counted backward from the most recently fully-elapsed week — the same "last week" indexing `applyMissedAdjustment` already uses, so "consistent" and "missed" are two readings of the same underlying measurement, not two independently-tuned thresholds that could disagree.

**Completion feedback is restrained, matching what the user's V1 request called for**: an ordinary completion still gets one of `CELEBRATE_MESSAGES`' calm rotating lines; a genuine milestone gets the existing AI-phrased `/celebrate` note or a plain "Highest weekly mileage yet: X mi." line; a newly-earned badge gets its own name(s) joined with " · " and "— nice work!" — never more than one message per save, and never guilt/streak-loss language for a skip or a miss (unchanged standing rule).

**Compatibility**: legacy installs that still carry `state.xp`/`xpEvents`/`xpProfile` from before this change have those fields explicitly deleted in `loadState()` (not just left un-migrated) — nothing reads them anymore and their numbers were never a real achievement worth preserving. `merge-state.js` no longer merges or emits `xp`/`xpEvents`/`xpProfile`/`quietGamification` at all, so a legacy device syncing with an upgraded one can never resurrect the removed XP UI on either side (`tests/merge-state.test.js`'s "legacy xp/xpEvents/xpProfile fields... never appear in the merged output" regression test proves this directly). Every other kind of history — workout logs, Side Mission log, badges, Path progress, personal records, plan data — is completely untouched by this change.

**Settings**: the "Reduce XP/level prominence" toggle (`state.flags.quietGamification`) is removed outright, not just hidden — with XP no longer visible anywhere, there was nothing left for it to quiet.

## Navigation / app reliability — P0 back-button fix + duplicate-submission guards (new 2026-08-03)

**P0 fixed: the browser/Android back button previously did nothing app-aware at all.** This app has no router — every screen is a full `#app` innerHTML swap via a `render*` function, with zero `history.pushState`/`popstate` wiring anywhere (confirmed by repo-wide search). That meant the system/browser back button always navigated the actual browser tab away from the app instead of moving between screens — a release-blocking navigation failure by any standard.

Fixed with a minimal, additive shim in `app.js` (`_navStack`/`_recordScreen`/`goBack`/a `popstate` listener) rather than introducing a router: every one of the app's ~19 top-level `render*` functions calls `_recordScreen(function () { renderX(sameArgs); })` as its first real statement (after any early-return redirect guard, so a screen that immediately redirects elsewhere never gets a phantom history entry of its own) — a zero-arg closure that can re-render that exact screen later. The very first screen of a page load replaces the history entry (never invents an extra one a reload would need two back-presses to clear); every subsequent screen pushes one. Every in-app "Back"/"Cancel" button (14 sites: Settings, Progress, Safety, Glossary, Coach chat, Path, workout/session detail, reschedule picker, switch-it-up, goal-change-confirm, Side Mission/Challenge detail) now calls a shared `goBack(fallbackRenderFn)` instead of calling a `renderX()` directly, so the browser's own back button and this app's own Back buttons always agree about what the previous screen was — both go through the identical `popstate` code path. At the true root, pressing back lets the browser's default action proceed (exiting the installed PWA / leaving the tab) rather than trapping the user behind a fake root.

This app has no separate modal/overlay layer distinct from a full-screen render (confirmed — screens like the reschedule picker and "Not feeling this run?" are themselves top-level renders, not overlays), so instrumenting every screen this way automatically satisfies "back from a modal closes it before leaving the underlying screen": going back from `renderSwitchItUp` naturally lands back on `renderWorkoutDetail`, live-verified in-browser.

**Duplicate-submission guards**: audited every button that appends to an array-based log (as opposed to a keyed upsert, which is naturally idempotent) for rapid-double-tap risk. `state.sideQuestLog.push(...)` is not idempotent — a double-tap on "Complete now"/"Complete Mission"/"Stop because of pain"/"Log progress"/"Mark unavailable"/"Add travel period"/"Add workout" could previously fire the handler twice before the following re-render removed the button, creating a duplicate completion/log record (inflating Side Mission counts, challenge progress, or weekly-challenge tallies). New shared `guardOnce(btn, handler)` disables a button synchronously on its first click, before the handler's own work runs, so a second queued click event is a no-op; call sites with their own field validation disable the button only after validation passes, so an invalid submission never permanently locks the control. `wdSaveBtn` (the workout log/save button) was also guarded for consistency even though `setLog`'s keyed-upsert design already made it non-duplicating — this just avoids a double-fired `/celebrate` AI call and a flickering double-toast. Weight-entry logging was checked and left alone — it was already upserted by date, genuinely idempotent.

**Update-available banner** (`app.js`/`style.css` `.update-banner`): `sw.js`'s activate handler already posted an `APP_UPDATED` message to every open tab the moment a new version took control (`skipWaiting`+`clients.claim`, deliberately not deferred until tabs close) — but nothing on the client side ever listened for it, so a deploy silently updated with no way for the runner to know or choose when to reload. Now a persistent (non-auto-dismissing, unlike the transient toast) banner offers Reload or dismiss; nothing forces a reload automatically, so current in-memory form/workout state is never lost mid-session.

**Also fixed**: a `scrollIntoView` call for the today-row auto-scroll on the main dashboard was missing the `prefers-reduced-motion` check the equivalent Path-screen scroll already had — brought into line.

## Run-walk programming — documented (fixed 2026-07-29)

A qualified running-coach review of this app (external, verbatim feedback) named this the top launch priority: a runner with no running background used to be forced straight into ~3 continuous running days and a shortened-but-still-continuous mileage plan — a scaled-down version of an experienced runner's plan, not a real beginner progression.

**Trigger**: a new onboarding question — *"Can you run continuously for a few minutes right now, without needing to walk?"* — stored as `profile.canRunContinuously` (defaults `true`; existing plans created before this question existed are unaffected). This is the explicit trigger, deliberately independent of `classifyUser`'s computed fitness tier — a low-frequency-but-continuous runner should never be routed into run/walk, and the master prompt itself names "run-walk ability" as its own distinct onboarding field, not something to infer from frequency/mileage.

**Structure**: `coaching-rules.js`'s `RUN_WALK_STAGES` (7 stages, own synthesis — a standard progressive time-based run/walk structure, not any single trademarked program's exact schedule), `runWalkStageForWeek`/`buildRunWalkSession`/`formatRunWalkLabel`/`runWalkWeeksFor`. `buildStructuredWeeks` (`app.js`) spends roughly the first 60% of the plan (minimum 4 weeks) on this progression for the long/quality/easy slots alike — **the quality slot's usual tempo/interval text is deliberately never shown during this window**, since a true beginner should never be handed "20 min tempo, comfortably hard" (the 10K entry-pool's actual content) before they can run continuously at all — then falls through to the normal continuous-mileage generator unchanged, so the runner arrives at race day already running continuously ("arrive ready," not still doing intervals in taper week).

**Data model**: day `type` stays `easy`/`quality`/`long` (unchanged) with an added `runWalk: {runSec, walkSec, cycles, totalMin}` field — a deliberate choice so XP (`xp-system.js` keys purely off `type`, never `miles`), `WORKOUT_DETAIL` lookup, `isLoggable`, and the logging form all keep working with zero changes, exactly as they already tolerate `miles: 0` for `quality`-type days today.

**Known gap, not fixed this pass**: `applyMissedAdjustment`/`applyDifficultyAdjustment` both key their volume-scaling off `day.miles` — a missed or hard-feeling run-walk session (`miles: 0`) won't get its own duration/intensity adjusted the way continuous days do, though it still correctly counts toward the missed-ratio (`type` is unchanged, so the existing exclusion logic for `rest`/`race`/`cross` days is unaffected). A real follow-up once this ships and sees actual use.

## Optional activity logging on rest days, and Google Health auto-sync — documented (new 2026-08-02)

**Rest days are now loggable.** `isLoggable(label)` (`app.js`) previously excluded rest days entirely — no log form, no Save button, no Google Health import button, nothing. A runner who walks, hikes, or otherwise moves lightly on a scheduled rest day (explicitly anticipated by that day's own "If I can't" copy: *"If you must move, keep it very light — a walk, not a workout"*) had no way to record it. `isLoggable` now returns `true` unconditionally; `isRest(label)` (unchanged) still separately drives the rest-specific description panel and calendar styling, decoupled from loggability itself. A rest day has no prescribed distance/pace, so `renderWorkoutDetail` shows a single-column "Logged" summary (not the two-column Planned/Actual table other day types get, which would otherwise render an empty Planned side) plus a distinct encouraging line rather than `interpretRunResult`'s plan-comparison phrasing. Logging one still runs through the same `logAndCelebrate` path as any other day — real XP, milestone detection (though `checkForMilestone` already excludes non-run types, so a rest-day walk is never compared against run PRs), the works.

**Google Health auto-sync.** Previously the only way to pull in Google Health data was `fetchActivitiesForDate` — a manual, single-day, user-clicked lookup from the workout detail screen. `GoogleHealth.autoSyncRecentActivity()` (`app.js`) now runs once at boot (right after `handleOAuthRedirect`, only if already connected) and automatically fills in any day in the current plan — rest days included — that doesn't already have a log entry, going back at most `GH_SYNC_MAX_LOOKBACK_DAYS` (14) days on a first sync or one after a long absence. A device-local cursor (`runner_gh_last_sync`, same "never on `state`, never synced" treatment as the tokens themselves) tracks the last date already checked; **today itself is always rechecked** on every boot, since new activity can still land later in the day, while everything before it is only ever checked once. If Google Health reports more than one session on a day, only the single largest-distance one is imported — a full multi-session-per-day model is out of scope for this pass.

Every import calls `logAndCelebrate` — **the exact same function a manual Save already uses**, not a separate parallel path — so an imported run gets real XP through the existing system, and a genuine personal best still gets the AI-phrased celebration via the existing `/celebrate` endpoint. This was a deliberate choice over building a second, new AI-backed "achievement" mechanism: the app already has a tested reward pipeline (XP ledger, level-up, milestone detection), and reusing it means an imported activity is treated identically to one typed in by hand, with no new OpenAI cost or duplicated logic. The imported entry's `notes` field is set to `"Imported from Google Health (<activity name>)"` so it's visibly distinguishable from a hand-typed log; no new state field or `merge-state.js` change was needed for this.

**Never overwrites, never touches race day.** A day that already has any log entry (manual or from a previous auto-sync) is skipped outright — this only fills gaps. The race day itself (`dayData.type === 'race'`) is never auto-filled, matching the same reasoning as the manual import path already had for the confirm-before-save Save button (a race result deserves a deliberate entry, not a silent auto-fill).

**Explicit gaps, not addressed this pass:** no completionType is set on an auto-imported entry (left `null`, which `xpForMainQuestWorkout`'s existing fallback already treats as full credit) — there's no way to know from Google Health's data alone whether an imported run matches what was actually prescribed that day, so it's left unclassified rather than guessed. No UI treatment yet distinguishes an auto-imported entry from a manual one beyond the notes text (e.g. no dedicated icon). A runner using multiple activity-tracking apps that each report the same session to Google Health could see it imported once and then re-imported if it later appears under a different session ID — not handled specially.

## Constraint-aware scheduling — documented (new 2026-08-02)

Extends the plan generator from "N running days placed by a static weekday priority" into a scheduler that respects the runner's actual weekday availability, richer recurring-commitment metadata, temporary travel schedules, one small conditional-preference rule, and a deterministic half-vs-10K readiness checkpoint. Built and verified end-to-end against a deliberately demanding real-life schedule (a runner with Mon/Wed/Fri/Sat/Sun running mornings, Tue/Thu reserved for a low-sweat 12-3-30 walk, a fixed Tuesday Tabata class, a fixed Wednesday circuit class, an every-other-week Friday Tabata class, a Monday 11am spin class, and a 2-week trip with an indoor-only city) — see `tests/constraint-scheduling.test.js`.

**Weekly availability (`profile.weeklyAvailability`, new, optional).** `{ [weekday 0-6]: { canRun: bool, window } }`. `weeklyAvailabilityCanRunSlots(profile, raceDate)` converts this to a set of plan slot indices (the long-run slot, always slot 6, is handled separately and excluded) and returns `null` — meaning "no override, use the legacy `RUN_SLOT_PRIORITY` ordering" — when the field is absent. `profile.availableDays` remains a fallback for the *count* of running days (`targetRunDaysFor`, unchanged) but never overrides *which* weekdays once `weeklyAvailability` exists, per the explicit backward-compatibility requirement. Onboarding gates this behind a "Do specific weekdays work better for running than others?" yes/no toggle (`app.js` logistics step) — answering "no" (the default) leaves `profile.weeklyAvailability` entirely unset, so the overwhelming majority of plans are byte-identical to before this feature.

**`AVAILABILITY_AWARE_PRIORITY`** is a *separate* constant from the legacy `RUN_SLOT_PRIORITY`, used only when `weeklyAvailability` is set. Same six slot positions, different preference: slot 5 (the day immediately before the long run at slot 6) is deliberately *last* here, protecting the long run from avoidable hard-session stacking the day before it — `RUN_SLOT_PRIORITY`'s own 3rd-priority placement of slot 5 predates that rule and is left unchanged for the legacy path (changing it would silently alter already-shipped plan output for every existing user). `buildStructuredWeeks` further reorders this per week: any slot with a same-day fixed commitment is pushed to the back of the order, so quality never lands on a day that already has a same-day class, without excluding that day from holding an *easy* run instead (a same-day fixed class only rules out that day being the week's hardest day, not a running day at all — e.g. a morning run followed by an 11am spin class is one ordinary day, not a conflict).

**Recurring activities, extended.** New activity types: `tabata` (always classified hard, regardless of the runner's own reported intensity — "Tabata counts as high intensity" is treated categorically, unlike every other type), `circuit` (real strength/fatigue load, intensity-dependent like cycling/hiit), `twelveThreeThirty` ("12-3-30," low-impact aerobic, never hard, can replace an easy/cross session). Every recurring-workout record gains, with safe defaults applied at *read* time via `normalizeRecurringWorkout` (never mutating stored data): `status` ('fixed'/'preferred'/'optional', defaulted from the legacy `fixed` boolean), `recurrence` ('weekly', the only possible prior behavior, or 'alternating'), `recurrenceAnchorIso`, `replaces` (defaults to the activity type's own `defaultReplaces`), `environment`, and `timeWindow` ('morning'/'midday'/'evening', `null` for every pre-existing record). **More than one fixed workout can now share a weekday** (e.g. a morning 12-3-30 and a noon Tabata both fixed on the same Tuesday) — `formatRecurringWorkoutsLabel` joins them into one label rather than the day only ever reflecting one.

**Same-day coexistence.** A fixed workout only overrides its weekday's slot outright when it has no stated `timeWindow`, or an explicit `morning` one — every pre-existing record (no `timeWindow` field at all) keeps its exact prior "occupies the whole day" behavior. An explicit `midday`/`evening` window on a slot that would otherwise be a running day lets the two coexist: the run keeps its type and gets the fixed workout's label appended (`day.secondaryRecurringWorkoutIds`), rather than the fixed workout silently erasing the morning run.

**Alternating recurrence.** `isRecurringWorkoutActiveInWeek(workout, weekStartDate, planStartDate)` re-evaluates every week (not once for the whole plan), toggling every 7 days from an anchor. **Regression caught in live browser verification, not by the unit tests alone:** the anchor must be `buildStructuredWeeks`'s own computed week-1 date (`planStartDate`), never the runner's raw typed start date and never the week currently being evaluated. `dateForSlot` anchors backward from the race date, so a plan's real week 1 can land a few calendar days before or after whatever the runner literally typed — using the typed date as the anchor silently flipped week 1's on/off parity in exactly this way during testing. Using the currently-evaluated week as its own anchor is equally wrong in the other direction (`weeksSinceAnchor` would always be 0, making every week "on"). New recurring-workout records leave `recurrenceAnchorIso: null` so this safe, always-week-1-is-active default applies; an explicit anchor remains available for a runner who wants a specific reference date instead.

**Hard-day stacking guard, two different rules depending on `weeklyAvailability`.** Without it (legacy, unchanged, still covered by `tests/recurring-workouts.test.js`): any hard fixed workout anywhere that week suppresses the plan's own quality session outright. With it: that blanket rule would wrongly suppress quality every week for a runner whose only hard fixed commitment is on a day she never runs anyway (this benchmark's Tuesday Tabata) — same-day conflicts are already handled by the priority reordering above, so what's left is a genuine weekly hard-day *count* cap (fixed hard workouts + the plan's own quality session capped at 2) rather than a blanket per-week suppression.

**Travel / temporary schedule overrides (`state.travelPeriods`, new, deliberately separate from `state.unavailable`).** `{ id, start, end, mode, indoorOnly, minDurationMinutes, preferredDurationMinutes }`, merged via `mergeMap`-by-`id` like `recurringWorkouts` (real edit-in-place). `applyTravelPeriods` (`coaching-rules.js`) replaces each affected day's session with a real indoor one instead of blanking it to rest: at most one "controlled" (quality-derived) session per travel week, the long-run day gets a deliberately *longer* session (`preferredDurationMinutes * 1.3`) when recovery/time permit, every session respects the stated minimum duration, `indoorOnly` sessions are always labeled treadmill/indoor and never imply an outdoor run, and exactly one day per travel week keeps being real rest (the first day that would have been anyway) — every other day, including days that would otherwise be blanket rest, becomes a short real session. A break of 7+ days gets the same proportional ramp-back the illness/away path already has for the week right after it ends. Settings gets a new "Travel" section, distinct from "Time off," with its own add/remove list.

**Conditional preference: unplanned evening intervals → next-morning hike/recovery.** One small, named, deterministic rule (explicitly *not* an unrestricted natural-language rules engine) — `applyEveningIntervalAdaptation` (`coaching-rules.js`), triggered by a log entry's `eveningIntervals: true` flag (a new toggle in the log form, `app.js`, user-set, never AI-inferred). The very next calendar day's quality/easy session is swapped to a shortened easy/recovery session; the long run and race day are protected outright and never silently downgraded.

**Goal decision checkpoint: half marathon vs. 10K.** `planMeta.checkpointDateIso` is set once at plan creation, only for a half-marathon goal, at roughly 45% through the build (early enough to still pivot with a real taper, late enough to reflect real accumulated evidence). `evaluateGoalCheckpoint` (`coaching-rules.js`) is a pure, deterministic function — real logged long-run distance, consistency (percentage of loggable sessions actually logged, restricted to days up to *today*, not the whole remaining plan), and pain flags, checked against the *same* `EVENT_TABLE` targets `evaluatePlanAdequacy` already uses. It **never mutates `raceGoal`** — it only returns a recommendation; `renderMain` shows a check-in card with explicit "Keep Half Marathon" / "Switch to 10K" buttons, and switching reuses the exact same event-change path (`finishWizard`) any other mid-plan goal edit already goes through.

**Explicit gaps, not addressed this pass:** the long-run weekday itself still always lands on the actual race weekday (unchanged, pre-existing architecture) rather than a separately statable "preferred long-run day" — for this benchmark customer the race falls on a Sunday, which is already one of her stated running mornings, so this didn't conflict, but a runner whose race weekday isn't one of her available days would see the long run land there anyway, with no separate warning surfaced for that specific case. The readiness checkpoint's evidence weighting (long-run distance, consistency, pain) is a first pass, not clinically reviewed. A runner using multiple recurring-workout apps/devices that report conflicting schedules isn't specially reconciled beyond the existing per-id merge semantics.

## Strength / mobility, environmental conditions, race execution — partially documented elsewhere

Strength/mobility content lives in the separate Side Missions system (`side-quests.js`, `docs/RACR_SideMission_Expansion.md`) rather than this document, since it's a distinct catalog with its own equipment/difficulty/safety-gating logic. Environmental-conditions handling (heat/altitude/terrain substitutions) and detailed race-week execution guidance are not yet formally specified anywhere beyond `WORKOUT_DETAIL`'s per-type descriptions — out of scope for this pass, not claimed as complete.
