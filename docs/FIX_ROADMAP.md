# Zaera — Fix Roadmap

Prioritized sequencing for everything found in `RELEASE_READINESS_AUDIT.md` / `RELEASE_BLOCKERS.md`. Effort estimates assume one engineer already familiar with this codebase.

**Update (2026-08-05):** this was originally written as a plan, not a change log — several items below have since actually been implemented by a follow-up audit. Each affected line is marked ✅ **Done** or 🟡 **Partial** with a short pointer to what changed; see `RELEASE_BLOCKERS.md`'s own per-item Status notes for full detail. Unmarked items are still exactly as originally planned — not yet started.

## Must fix before closed testing (once internal testers have used a real build)

1. 🟡 **Partial** — **Add crash reporting** (`RELEASE_BLOCKERS.md` CRITICAL-2) — without this, feedback from a wider tester group is the *only* way bugs surface. *0.5–1 day.* `window.error`/`unhandledrejection` hooks now POST to `netlify/functions/log-telemetry.js` (Netlify function logs, no third-party account). Still no dashboard or alerting — someone has to know to go tail the logs.
2. 🟡 **Partial** — **Add minimal analytics** (`RELEASE_BLOCKERS.md` CRITICAL-3) — closed testing is exactly when you want real usage signal on the newest features (Side Missions, Path, XP/challenges) before a production audience sees them. *1–2 days.* Same `log-telemetry.js` pipeline now emits `onboarding_completed`/`workout_logged`/`workout_skipped`/`side_mission_completed`/`challenge_completed`/`ai_call_failed`. Still no aggregation/dashboard — raw log lines only.
3. **Fix the highest-impact accessibility gaps**: label the icon-only header/tab-bar buttons with `aria-label`, add `role="progressbar"`/`aria-valuenow` to the Path/Quest/Challenge progress bars. Play's own automated Pre-launch report will flag these regardless — better to have already fixed the obvious ones than to discover them there first. *1–2 days for the highest-traffic screens.* (Not reverified this round — check current state before assuming still open or already done.)
4. ✅ **Done** (for the four functions originally scoped) — **Extract and test `mergeRunnerState` + the plan generator** (`RELEASE_BLOCKERS.md` CRITICAL-1, scoped to the highest-value subset) — closed testing is exactly the phase where a silent data-loss bug in cross-device sync would otherwise go unnoticed until a real tester reports "my plan disappeared." *2–4 days.* `mergeRunnerState` → `merge-state.js`, `buildStructuredWeeks`/`classifyUser`/`evaluateSafety` → `coaching-rules.js`, both fully tested (326 total tests). Went further than scoped: found and fixed 3 real bugs, including a systemic cross-device deletion-resurrection gap across 10 different state fields. **The rest of `app.js` (~140 functions) is still untested** — see CRITICAL-1's updated status and "Can wait until after launch" item 1 below, which is not actually safe to leave until after launch given what this round found.
5. **Add a CI workflow** running `npm test` on every push/PR — cheap insurance against a regression reaching testers unnoticed. *0.5 day.* (Still absent — no `.github/workflows/`.)

## Must fix before production (open/public release)

1. **Full accessibility pass**: touch-target sizing, color-contrast review, `prefers-reduced-motion`, focus-order review across every screen — not just the highest-traffic ones. *3–5 days.*
2. **Resolve the whole-object last-write-wins sync gap** for `raceGoal`/`profile`/`planMeta` (`RELEASE_READINESS_AUDIT.md` Section D) — apply the same union/ledger pattern already proven for `xpEvents`/`sideQuestLog` this session. *2–3 days.* **Note (2026-08-05):** `xpEvents` no longer exists (removed along with the whole XP/generic-levels system). More importantly, re-examine this item's premise before starting it: this round's audit treated `raceGoal`/`profile`/`planMeta`'s wholesale-prefer-newer-device merge as the *correct*, intentional pattern — it's the same one used to fix a real bug in the `path` field (see `merge-state.js`), and per-field merging doesn't obviously make sense for a single owned object like a race goal. Confirm there's still a real gap here (and what it actually is) before treating this as validated scope.
3. **Minify/bundle `app.js`** (even a simple minifier pass without a full bundler rewrite would meaningfully cut the ~244 KB payload) — matters most for the lower-end Android devices most likely to represent a real free-app user base. *1–2 days, more if a real bundler + build step is introduced.*
4. **Write a Terms of Service** and confirm the `support@zaeralabs.com` mailbox is real/monitored before either document is linked from a public Play listing. *0.5 day + external verification.*
5. **Decide the notification-reliability messaging** — either build real push (Web Push + VAPID + a scheduled server function + per-user subscription storage, a materially larger feature) or make sure the in-app copy never implies reminders work while the app is fully closed, so expectations match reality before a wider audience forms opinions from a broken promise. *Messaging fix: 0.5 day. Real push: 1+ week, separate project.*
6. **Pin the Supabase CDN script to an exact version** instead of the floating `@2` tag, to avoid an unannounced upstream change silently breaking auth/sync in production. *15 minutes.*

## Can wait until after launch

1. Full extraction/testing of every remaining pure function in `app.js` beyond the highest-value subset already covered pre-closed-testing. **Caveat (2026-08-05):** this round found a real, live bug in exactly this untested remainder — `applySideQuest`/`applySideQuestChat` could silently fail to persist a side-quest swap despite showing a success toast — purely from manual code reading, no test needed to exist first. "Can wait" was reasonable when this was a theoretical risk; it's now a demonstrated one. Recommend at least a targeted read-through pass (not necessarily full extraction+tests) of the remaining ~140 functions before launch, prioritizing anything else that mutates state without an obvious save path.
2. A real Lighthouse/performance budget wired into CI.
3. List virtualization for very long (50K/100-mile) training plans, if usage data (once analytics exists) shows this is actually a real-world pain point rather than a theoretical one.
4. Time-zone-aware date handling for users who travel mid-plan, if usage data shows this actually occurs and causes confusion.
5. Real push notifications (if not already prioritized into the pre-production phase above).
6. Any subscription/monetization flow and its associated Play disclosure work — entirely out of scope until a monetization decision is made.

## Sequencing rationale

The order above deliberately front-loads **observability** (crash reporting, analytics, CI) before deeper structural fixes, because every later phase — accessibility triage, sync-conflict fixes, performance work — is far more efficient with real crash/usage data in hand than working from source-code inspection alone, which is all this audit could use. The single highest-leverage non-packaging fix is extracting `app.js`'s pure logic into testable modules, since it is both the riskiest untested code in the project and the one most likely to produce a genuinely bad, hard-to-diagnose user-facing bug (silent data loss) if left alone through a period of increasing real usage.

**Update (2026-08-05):** the sequencing logic above held up. Observability landed first (minimal telemetry, not a full SDK) and the sync-conflict logic got extracted and tested exactly as prioritized — and that extraction immediately paid for itself, surfacing 3 real bugs (a systemic cross-device deletion-resurrection gap across 10 state fields, plus the `path` field's own separate bug) that had shipped silently until now. What's changed: CI (item 5 of closed-testing) is still not done despite being cheap, and is now more valuable than when this was written, given there's real test coverage worth protecting from regression. Recommend moving it up in priority rather than leaving it last in that section.
